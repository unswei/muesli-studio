# v1.0 product plan

## what this is

This page is the source of truth for the `muesli-studio` path to `v1.0`.

The goal is to make Studio an evidence-grade inspector, comparison, and controlled repair tool for `muesli-bt` runs. The product should help users replay runs, follow live systems, understand failures, compare behaviour, make bounded behaviour tree edits, and export reproducible evidence.

## when to use it

Use this plan when deciding what belongs in the release roadmap, the current `TODO.md`, public docs, website copy, release notes, or exported bundle text.

The plan is for Studio only. Runtime work in `muesli-bt` matters only where Studio consumes the public contract, event schema, capability metadata, or replay artefacts.

## how it works

The work is organised by release milestone rather than calendar dates. Each milestone has one dominant product outcome and a small set of acceptance criteria.

Public language must stay product-focused. The repository, docs, website copy, UI text, release notes, and exported bundle templates must not reveal private research plans or non-product strategy. Generic uses such as talks, reviews, reproducible evidence, and papers are acceptable only when they describe ordinary product use.

Studio may inspect host capability, model-call, validation, provenance, and replay metadata. Studio must not become a broad robot-control interface, a general robotics IDE, or a replacement for `muesli-bt` host tooling.

## milestones

### milestone 0: plan and public-language alignment

Document this plan, update the release roadmap, refresh the TODO list, and audit public language.

Acceptance criteria:

- this page exists and is linked from the roadmap and README
- the roadmap uses release milestones, not date-based planning
- `TODO.md` contains the immediate next implementation slice
- public-facing docs and bundle text avoid private research framing

### v0.5: validation-aware editing and capability context

Finish the disciplined behaviour tree editing workflow and sharpen it around evidence needs.

Acceptance criteria:

- users can inspect a structural diff before applying a tree edit
- capability-related validation is visible without becoming a control surface
- edited-tree evidence can be saved or exported
- tests cover capability diagnostics, edit previews, and replay mismatch warnings

### v0.6: run comparison and regression evidence

Make comparison useful for repaired behaviour, regressions, and review.

Acceptance criteria:

- users can compare a failing run against a repaired run without external tooling
- comparison output identifies first divergence and high-signal behavioural changes
- exported comparison reports are deterministic enough for regression tests
- tests cover summary deltas, first-divergence selection, and saved report contents

### v0.7: integration and model-call inspection

Make backend-rich runs understandable without making the UI backend-specific.

Acceptance criteria:

- users can understand why an output was accepted, rejected, stale, cancelled, or ignored
- provenance is visible in context and in exported evidence
- canonical demos cover the main `v1.0` inspection questions
- tests cover lifecycle grouping, provenance rendering, and event explorer jump targets

### v0.8: evidence bundle and presentation polish

Turn the existing presentation and export paths into a polished evidence-bundle workflow.

Acceptance criteria:

- a bundle can explain a run, a failure, a comparison, and a repair without private context
- bundle README text is product-safe
- screenshots are stable across regeneration
- tests cover manifest shape, bundle README text, and export contents

### v0.9: hardening and user-study readiness

Stabilise the product surface and make Studio measurable as a debugging and repair tool.

Acceptance criteria:

- the main workflows are coherent from live capture to replay, compare, repair, and export
- study materials can be published as normal product evaluation artefacts
- performance remains acceptable on large indexed logs
- the full test, build, fixture validation, and screenshot generation path passes

### v1.0: stable evidence-grade Studio

Declare `v1.0` when Studio is stable as the default way to inspect, understand, compare, carefully edit, and export evidence from `muesli-bt` runs.

Acceptance criteria:

- replay, live capture, comparison, controlled editing, lifecycle inspection, and export work as one coherent product
- public docs, README, release notes, and website copy tell the same product story
- release notes include compatibility, migration notes, known limits, and verification steps
- `TODO.md` contains only post-`v1.0` work after completed tasks are removed
- `CHANGELOG.md` records the `v1.0` changes

## api / syntax

Preserve the existing event schema unless upstream `muesli-bt` adds lifecycle fields that Studio must consume.

Extend Studio bundle manifests conservatively for comparison reports, edit artefacts, provenance, lifecycle summaries, and redaction notes. Treat saved comparison reports and exported edit artefacts as product-facing formats once documented.

Use product-facing labels such as:

- evidence bundle
- export bundle
- comparison report
- repair workflow
- presentation mode

Avoid labels that imply private non-product strategy.

## example

A good `v1.0` flow should look like this:

1. Connect to a live run.
2. Pin an interesting tick.
3. Save the live capture.
4. Reopen it as a replay.
5. Compare it with a repaired run.
6. Inspect the first divergence and validation context.
7. Export an evidence bundle with replay data, summary, screenshots, comparison report, and reproduction notes.

## gotchas

- Do not add broad visual authoring to solve narrow repair needs.
- Do not expose host capabilities as arbitrary robot-control buttons.
- Do not make public docs depend on private research context.
- Do not let TODO, roadmap, release notes, and website copy drift apart.
